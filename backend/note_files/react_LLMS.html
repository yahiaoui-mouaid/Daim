The Basic React Data Flow

Four layers, each with one job. Click any card to expand details, or tap the nodes in the chain below.

Page / Component
pages/DashboardPage.jsx
▼

What the user sees. It calls a function to get data and renders whatever comes back.

It should not know how the request is made — just that it needs data. This keeps your components clean and testable.

🔌
Service
services/notes.js
▼

A function like getNotes() that calls api.js with a specific endpoint.

This is where you'd add getCurrentUser() for /api/auth/users/me/. Services keep URL logic out of your components.

🌐
api.js
utils/api.js
▼

Your central request client (axios instance or wrapped fetch). This is where:

• The base URL lives (http://localhost:8000/api)
• The access token gets attached as Authorization: Bearer
• A response interceptor catches 401s, tries silent refresh, retries the request

🧠
Context
context/AuthContext.jsx
▼

Holds the in-memory access token and user state, exposing them (plus login/logout) via useContext.

This is the glue between "I'm logged in" and the rest of the app.

Your Specific Token Flow

HttpOnly cookie + memory access token. This is what makes your setup different — and what LLMs get wrong.

⛔Access Token — Memory Only
Lives exclusively in AuthContext state (React memory). Never localStorage. Never a normal cookie JS can read. This is the #1 thing LLMs get wrong.
🍪Refresh Token — HttpOnly Cookie
Set by Django. The browser sends it automatically on refresh requests. JavaScript never touches it directly — this is the whole point of HttpOnly.
⚙️withCredentials: true
Your axios instance needs withCredentials: true (or credentials: 'include' for fetch) so the HttpOnly cookie is sent on the refresh call.

⚠️ Critical for LLM Output

Any time you ask an LLM to build something touching auth, restate these three constraints. The LLM's default instinct is to store tokens in localStorage — the wrong pattern for your setup. The wrong output here silently reintroduces localStorage or breaks refresh-on-mount.

// api.js — the non-negotiable bits
                        const api = axios.create({
                        baseURL: 'http://localhost:8000/api',
                        withCredentials: true, // ← HttpOnly cookie works
                        });

                        // Request interceptor — attach access token
                        api.interceptors.request.use(config => {
                        const token = useAuthStore().accessToken; // memory only
                        if (token) {
                        config.headers.Authorization = `Bearer ${token}`;
                        }
                        return config;
                        });

                        // Response interceptor — silent refresh on 401
                        api.interceptors.response.use(
                        response => response,
                        async error => {
                        if (error.response?.status === 401) {
                        // POST /auth/jwt/refresh/ — cookie sent automatically
                        const newToken = await refreshAccessToken();
                        // retry original request with new token
                        }
                        return Promise.reject(error);
                        }
                        );
Section 3

What to Tell the LLM

Five things, in this order. Give it your real files — that's the single biggest lever you have.

A Exact task & endpoint ▼

"Create a page pages/ProfilePage.jsx that fetches the logged-in user's data from GET /api/auth/users/me/ and displays [name/email/whatever fields]."

B Your project's existing conventions ▼

Paste the relevant files, don't describe them.

• Paste your actual api.js
• Paste your actual AuthContext.jsx
• Paste one existing service file (e.g. notes.js)
• Paste one existing page (e.g. HomePage.jsx)

This is the single biggest lever you have.

An LLM given your real api.js will reuse your interceptor and header pattern. An LLM given only a description will invent its own — usually wrong for your setup.

C The auth constraint, explicitly ▼

"Access token is stored in memory via AuthContext only. Refresh token is an HttpOnly cookie, never touched by JS. Do not use localStorage or sessionStorage. Use the existing api.js instance for the request — don't create a new axios/fetch call."

D The response shape ▼

If you know the JSON structure, paste an example. Otherwise the LLM will guess field names.

"assume fields": id, email, username, role

E Loading / error expectations ▼

"Show a loading state while fetching, and handle the case where the request fails (e.g. redirect to login if 401 persists after refresh)."

📌 Full "Must-Provide" Checklist

Check off items as you prepare your prompt. Your progress is saved locally.

💡 Pro tip: Paste those five files once at the start of a session. After that, you can say "same pattern, new endpoint: /api/notes/{id}/" — and it'll stay consistent without re-explaining the token architecture every time.
