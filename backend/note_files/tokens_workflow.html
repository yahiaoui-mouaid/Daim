سأشرح لك تدفق العمل (workflow) بالكامل

من لحظة إدخال المستخدم لبياناته إلى حماية الصفحات، بناءً على النظام الجديد (access token في الذاكرة/localStorage + refresh token في httpOnly cookie).

1. عملية تسجيل الدخول (Login)

  1. المستخدم يدخل الإيميل وكلمة المرور في loginForm ويضغط submit.
  2. الفرونت إند يرسل طلب POST إلى /api/token/ عبر axios، مع withCredentials: true (هذا الإعداد مهم جدًا — بدونه المتصفح لن يقبل أو يرسل الـ cookie لاحقًا).
  3. على الباك إند، CookieTokenObtainPairView يستقبل الطلب، يتحقق من صحة البيانات عبر SimpleJWT، وينتج access token و refresh token معًا.
  4. هنا يحدث الفرق الجوهري عن النظام القديم:
    • الـ access token يبقى في جسم الاستجابة (JSON body) ويُرسل للفرونت إند بشكل طبيعي.
    • الـ refresh token يُستخرج من الاستجابة (response.data.pop("refresh")) ولا يُرسل في الـ JSON إطلاقًا، بل يُوضع داخل httpOnly cookie باسم refresh_token.
  5. الفرونت إند يستقبل الاستجابة، ويحفظ الـ access token في localStorage (عبر ACCESS_TOKEN). أما الـ refresh token — فهو لا يراه أصلاً، لأن المتصفح يخزّن الـ cookie تلقائيًا خارج متناول أي كود JavaScript.

2. حماية الصفحات (ProtectedRoute)

عند فتح أي صفحة محمية:

  1. ProtectedRoute يتحقق أولاً هل يوجد access token في localStorage.
  2. إذا لم يوجد → المستخدم غير مسجل دخول → تحويل إلى /login.
  3. إذا وُجد → يُفك تشفيره محليًا عبر jwtDecode لقراءة تاريخ الانتهاء (exp) فقط (بدون التحقق من التوقيع، فهذا عمل الخادم).
  4. إذا كان منتهي الصلاحية → يُستدعى refreshAccessToken().

3. تجديد الـ access token (Refresh)

هذه هي النقطة التي تغيّرت جذريًا:

  1. الفرونت إند يرسل POST إلى /api/token/refresh/ بدون أي body — لا حاجة لإرسال أي refresh token يدويًا.
  2. بفضل withCredentials: true، المتصفح يُرفق الـ httpOnly cookie تلقائيًا مع الطلب — وهذا يحدث على مستوى المتصفح نفسه، لا على مستوى كود JavaScript.
  3. على الباك إند، CookieTokenRefreshView يقرأ التوكن من request.COOKIES.get("refresh_token") بدلاً من انتظاره في جسم الطلب.
  4. SimpleJWT يتحقق من صلاحية الـ refresh token، وإذا كان صالحًا يُصدر access token جديد (وربما refresh token جديد إذا كان ROTATE_REFRESH_TOKENS مفعّلاً — وفي هذه الحالة يُعاد وضعه في الـ cookie أيضًا، وليس في الـ body).
  5. الفرونت إند يستقبل الـ access token الجديد فقط، ويحدّثه في localStorage.

4. لماذا هذا التصميم أأمن؟

  • إذا حدث اختراق XSS في موقعك (سكربت خبيث يعمل داخل الصفحة)، فبإمكانه في أسوأ الأحوال قراءة الـ access token من localStorage — لكنه قصير الأجل، فالضرر محدود بوقت انتهائه.
  • لكن الـ refresh token — الذي يبقى فعالاً لساعات أو أيام — لا يمكن لأي كود JavaScript الوصول إليه إطلاقًا، لأنه محمي بخاصية httponly. حتى لو تم اختراق الصفحة بالكامل عبر XSS، هذا التوكن يبقى بمنأى عن السرقة.

5. تسجيل الخروج (Logout)

CookieTokenLogoutView يحذف الـ cookie الخاص بالـ refresh token من طرف المتصفح (delete_cookie). للحماية الكاملة، يُفضّل لاحقًا تفعيل token_blacklist من SimpleJWT حتى يُبطَل التوكن فعليًا من طرف الخادم أيضًا، وليس فقط حذفه من المتصفح.

هل تريد أن أشرح أيضًا نقطة ROTATE_REFRESH_TOKENS أو أضيف صفحة Logout في الفرونت إند بنفس الأسلوب؟
